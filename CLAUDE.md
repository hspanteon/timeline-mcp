# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small Python MCP (Model Context Protocol) server, built with FastMCP, that fetches task data and conversation history from Panteon Timeline (`https://timeline.panteon.no`) and renders it to markdown. It exposes MCP tools `get_task_conversation`, `get_my_priority_tasks`, `get_my_planner_changes`, `get_my_day`, `get_task_statuses` and `check_auth` and one MCP resource (`timeline://<issue_id>/task.md`), plus an equivalent CLI (`fetch_task.py`) for shell use and a local web dashboard (`dashboard.py` + `release_check.py` + `work_session.py` + `workflow.py` +  + `web/`).

## Architecture

Three files carry all the logic; keep the same separation when adding to them:

- **`panteon_client.py`** — everything that isn't MCP-specific: URL/issue-ID parsing, the two Panteon API calls, response parsing, image extraction, markdown rendering, and the `fetch_task_data` / `fetch_and_save` orchestration functions. This is the file to add unit tests against — its helpers are pure/deterministic and mock only `requests.get`.
- **`server.py`** — FastMCP tool/resource registration only. Calls into `panteon_client` for all real work, running the synchronous/blocking client off the event loop via `anyio.to_thread.run_sync`.
- **`fetch_task.py`** — thin CLI wrapper over `panteon_client.fetch_and_save`, kept in sync with the MCP tool by using the same shared orchestration function.

### Two-step API resolution

Fetching a task mirrors the reference browser extension's logic and always happens in two calls:
1. `GET /api/taskbyissue/{issue_id}/{company_id}` — resolves the external, user-facing issue ID (e.g. `5461`) to Panteon's internal `task_id`.
2. `GET /api/task/{task_id}/timeline` — fetches the full timeline, from which comments are filtered out via `parse_conversation_comments`.

`extract_issue_id` only accepts a bare numeric ID or a URL containing `/edit/<id>` — it deliberately does NOT fall back to "trailing digits" in the URL, since a list/board URL like `.../list/15033` would otherwise silently resolve to the wrong (board) ID.

### Employee planner

`get_my_priority_tasks` (and `fetch_task.py --planner`) call `GET /api/employee-planner/get-priority-tasks/{period}` (`now`, `next`, or `commingup` — the API's spelling), which returns **every** employee's planner (`[{user_id, data: [task, …]}]`). `fetch_my_priority_tasks` filters it to one user: `resolve_user_id` takes the explicit argument, then `PANTEON_USER_ID`, then the bearer JWT's `sub` claim. A user absent from the planner raises `LookupError` (wrong id), distinct from a user with zero tasks. `normalize_planner_period` rejects any other period — including the single-m `comingup` — because the API silently returns every task for an unknown segment. The rendered table is returned, not written to disk. A task's `code` is its list/board id, so its URL is `/tasks#/list/{code}/edit/{issue_number}`. `deadline_flag` marks deadlines as overdue, due today or due within `DUE_SOON_DAYS` (7); `render_priority_tasks_markdown` takes an optional `today` so tests stay date-independent — always pass it in tests.

`get_my_planner_changes` (and `fetch_task.py --changes`) fetches all three periods, builds a snapshot of the user's tasks keyed by issue number (`build_planner_snapshot`; a task in several periods keeps the earliest), and diffs it (`diff_planner_snapshots`: added, removed, moved, changed deadline/stage/status; priority is the order of the tasks both snapshots share in a period, so a task added on top is not a change for those below it; stages and release state are compared only when both snapshots carry them) against the latest snapshot from an **earlier** day (`load_previous_planner_snapshot`), so same-day reruns are stable. Snapshots live in the SQLite file `<base>/database/timeline_task.db` (`planner_db_path`; `database/` is gitignored; tables `snapshots` and `checks`; reads never create it). `save_planner_snapshot` only inserts a row when the tasks differ from the user's latest stored snapshot, and always records the check time in `checks` (`last_planner_check`), so frequent polling stays cheap and every row is a change; priority position alone doesn't count. Each snapshot carries `taken_at`; the first open of the DB imports any old `timeline/planner/<date>.json` files once. `fetch_my_planner_changes` takes `today`, `now` and `base_dir` for tests, and `with_stages` (dashboard only: one extra taskbyissue call per task, stored as `stages`, `release_state`, `qa_approved`; a snapshot without them inherits the latest stored ones, see `_carry_forward_stage_details`).

`get_my_day` (and `fetch_task.py --my-day`) is the daily brief: `fetch_my_day` calls `fetch_all_planners` once (one request per period) and hands the result to `fetch_my_planner_changes(planners=…)` so no period is fetched twice. It composes the now table, soon-due `next` tasks and the changes under one `# My Day` header, using the renderers' `title`/`level` arguments (level > 1 drops the per-section User ID line). Keep new planner features on this shared fetch rather than adding calls.

In `server.py`, every client call goes through `_run_client`, which runs it off the event loop and maps `ValueError`/`LookupError`/HTTP/connection errors to `ToolError`; don't repeat that try/except in new tools. Output paths all derive from `timeline_dir`.

### Workflow stages

`get_task_statuses` (and `fetch_task.py --status`) calls only API 1 (`taskbyissue`) per task, in a small thread pool, and writes nothing. Timeline tracks six stages (`TASK_STAGES`: `stage_rsd`, `stage_est`, `stage_dev`, `stage_tst`, `stage_qa`, `stage_liv`), each with a progress code (`STAGE_PROGRESS`: 0 not started, 1 skipped, 2 in progress, 3 blocked, 4 done — inferred from live data across every `stage_status`). `task_status` is `open` for every live task, so `release_state` derives the signal from the QA and Live codes, and `qa_approved` means QA done or already live. taskbyissue answers an unknown issue with HTTP 422 (also 404), which becomes a per-row `not found` instead of failing the batch; other HTTP and auth errors still raise.

### Dashboard

`dashboard.py` is a Starlette app (Starlette and uvicorn come with FastMCP, so no extra dependency) serving `web/` (plain HTML/CSS/JS, no build step) and a small JSON API: `/api/planner` (`planner_overview`), `/api/changes` (`planner_history` over the saved snapshots), `POST /api/snapshot` (the Refresh button on the Changes tab), `/api/statuses?ids=…` (`get_task_statuses`, max 100), `/api/task/{issue}` (`fetch_task_data`, nothing written), `GET /api/release` (the cached release report, or null) and `POST /api/release` (rebuild it). Keep the data shaping in `panteon_client.py` and the endpoints thin; `_respond` maps client errors to JSON (401 auth, 404 not found, 400 bad input, 502 upstream). Sync endpoints run in Starlette's threadpool.

Security rules for the dashboard — keep them when changing it: bind `127.0.0.1` only; `TrustedHostMiddleware` allows only `ALLOWED_HOSTS` (`127.0.0.1`, `localhost`, `timeline.localhost`; blocks DNS rebinding); no CORS; state-changing endpoints require the `X-Timeline-Desk: 1` header (a cross-site form can't send it); the page loads no external fonts or scripts and sends no referrer; all Timeline text is inserted with `textContent` / DOM nodes (`h()`, `richText()` in `app.js`), never `innerHTML`. Tests are in `tests/test_dashboard.py` (Starlette `TestClient`). `web/` files are served with `Cache-Control: no-cache`; in `app.js` use `put(el, …)` rather than `el.replaceChildren(…)`, because `put` skips null children the way `h()` does.

The Help page (`#/help`, `showHelp` in `app.js`) documents where each page gets its data (live Timeline, in-memory copy, SQLite, git), its refresh interval and how it works; the text is in `web/help.js` and the source icons next to the tabs are `SOURCE_ICONS` / `PAGE_SOURCES` in `app.js`. When a page's data source or refresh behaviour changes, update `help.js` and `PAGE_SOURCES`. Scheduler intervals, workflow steps/buttons and run statuses are read from `GET /api/about` (`SCHEDULE` in `dashboard.py`), so they cannot drift.

`main()` also starts a daemon thread (`run_snapshot_scheduler`) that polls in tiers so it feels live without request spikes: every heartbeat (`--heartbeat` / `TIMELINE_HEARTBEAT_MINUTES`, default 3) it reads only the `now` planner period (1 request, compared by `planner_fingerprint`) plus each watched task's timeline (`sync_watchlist(refresh_meta=False)` reuses the stored `task_id`, so 1 request per task). The full planner check (3 periods, reusing the fetched `now` via `fetch_all_planners(known=…)`) runs when the fingerprint changed or every `--interval` / `TIMELINE_SNAPSHOT_MINUTES` (default 15); stage lookups (1 request per task) only on a change or hourly, and carried-forward stage details fill the gaps. Outside the active hours (weekdays, `TIMELINE_ACTIVE_HOURS`, default `7-19`, `all` disables) it does one full check an hour; waits are jittered ±10%. `_pace` in `panteon_client` also spaces out the start of every API call (`PANTEON_MIN_REQUEST_GAP_MS`, default 200, 0 = off), so bursts become a trickle. Failures are logged, not fatal. `/api/changes` (`planner_history`) returns `{tracking_since, last_checked, changes: [{taken_at, previous_taken_at, diff}]}` newest first, one entry per detected change with its time, and the Changes page re-fetches it every minute while open.

`task_events.py` keeps the per-task event history behind the Timeline tab. Timeline already stores every event of a task (`/api/task/{id}/timeline`: status, comment, commit, deadline, hours, group, … each with a global id, author and `dd.mm.yyyy HH:MM` time), so history is copied, not inferred from snapshots. Tables `watchlist` and `task_events` live in the same SQLite file (schema version 2 in `_open_planner_db`; version 3 adds the workflow tables). Only watched tasks are fetched, never all tasks: a task is watched by hand (the Watch button on the Task tab's lists → `POST /api/watchlist`, which accepts any task that exists in Timeline and is not closed (`task_status` `closed`): one taskbyissue call gives its title and project, and the project's list code comes from `timeline-desk.json` when it is set up there), and `DELETE /api/watchlist/{issue}` only pauses it (events stay). `sync_watchlist` does taskbyissue + timeline per active task (small thread pool), inserts with `INSERT OR IGNORE` on the event id (first sync backfills, later ones add only new events), records a per-task `last_error`, and pauses a task once its `task_status` is `closed`. It runs every heartbeat in the scheduler and on the Refresh button (`POST /api/events/sync`); `GET /api/events` pages newest-first (`issues`, `kinds`, `before` cursor). Comment/commit rows carry placeholder old/new values ("Old value"), which `parse_event` drops. Times are Timeline's own naive clock; ties order by event id. The page hides commits unless toggled on. Tests: `tests/test_task_events.py` (event ids in fakes must be unique across tasks, as they are in Timeline).

`workflow.py` is the task workflow behind the Task page's panel (history, known phase 1 issues and the plan for phases 2–5: `docs/workflow-roadmap.md`; read it before changing workflows): a fixed flow (`FLOW`: intake, estimate (optional), develop (repeats, one implementation step per run), review, release_qa, qa (a decision: QA found issues / approved), qa_fix (repeats, one finding per run, then back to qa with `qa_round` + 1), release_prod, close), kept in the planner SQLite file (schema version 3: `workflows` one row per task, `workflow_runs` every Claude run, `workflow_events` every decision with its time and note). Nothing moves without a decision: `actions(wf, runs, has_analysis)` lists what is possible now (run, approve, reject, resume, abandon, finish, skip, back_to_develop, qa_issues, qa_passed, close, stop, reopen), the page renders exactly those buttons, and `run_step` / `resume_run` / `decide` refuse anything not in that list (`_allowed`), so the rules live in one place. Skip, reject, abandon and back_to_develop need a note; stop doesn't (just a confirm). A run step opens `claude --session-id <uuid> <prompt>` in a terminal in the task's worktree (normal permission prompts); `build_prompt` holds only the issue ID and fixed text (never task content), names the lifecycle skills by path under `skills/`, and ends with the report contract: write `timeline/<id>/runs/<run>.result.json` (`status` done/needs_input/blocked/failed, `summary`, `files`, `commits`, `questions`, `remaining` for repeating steps). The terminal writes `<run>.exit` when Claude exits. `refresh_run` copies both into the run row on every read (`clean_result` keeps only known keys, capped), and `run_status` derives running / review / needs_input / blocked / failed / bad_result / no_result / approved / rejected. Resume deletes both files (the old result stays in the event note) and runs `claude --resume <session>`. `read_transcript` shows a run's conversation from Claude Code's session log (`<CLAUDE_CONFIG_DIR or ~/.claude>/projects/*/<session>.jsonl`; text and tool calls only); `read_doc` serves `timeline/<id>/*.md|sql|txt` from the main checkout by a fixed name pattern. `propose_start` suggests the first step from Timeline's stages and whether analysis.md exists. Endpoints: `GET /api/workflows` (badges), `GET /api/workflow/{issue}?code=` (the whole view; one taskbyissue call only when no workflow exists, for the suggestion and, without `code`, the board: its `project_id` matched to the repo `id`s by `work_session.board_for_project`), header-guarded `POST …/start|run|resume|decide` (start and run re-read the stages: Develop and Fix QA refuse a blocked task), `GET …/doc/{name}`, `GET …/runs/{id}/transcript`. Tests: `tests/test_workflow.py` (real git in tmp, recording launcher, fake session log).

Phases 2–5 extend it (details and what's unverified: `docs/workflow-roadmap.md` §10). Phase 2: workflow tasks are auto-watched; `signal_for` / `workflow_signals` turn unseen `task_events` (after `seen_event_id`) into signals that suggest actions (never run them); `ack` marks them seen; `"me"` in `timeline-desk.json` drops your own comments; side run `unblock` (SIDE steps never move the flow); Workflows tab. Phase 3: comment ids in `task.md` headings; `qa_findings` (`_sync_findings`, `classify_finding`, `add_finding`), one finding per Fix QA run by comment id, `qa_reply` drafts, `prod_fix` → `release_hotfix` after close, workflow badges on the Release tab. Every run is an interactive Claude Code session in a terminal (`run_step` has no other mode): no background process, no `claude -p`, no Agent SDK, no approvals on the page; Claude's own permission prompts in the terminal are the only approvals. (Phases 4 and 5 once ran steps in the background and inside the dashboard; both were removed on 2026-10-28, see `docs/workflow-roadmap.md` §10.9. Their `mode`/`pid` columns and the empty `workflow_permissions` table stay in the schema, unused.) What the open terminal is doing shows on the run card and the status badges: `terminal_activity` reads the tail of Claude's session log (last tool call or message, and the log's age: starting, working, running a tool, waiting on a tool call, asking a question, waiting for your message), and the page re-reads every 5 s while a run is open. "Waiting on a tool call" can't tell a long command from an approval prompt, so it says both. Every run gets the desk's own timeline MCP server via `--mcp-config` (`work_session.MCP_NAME` = `timeline-desk`, `mcp_config` / `mcp_server`), because a project can disable `timeline-mcp` and Claude Code applies that to the repo's worktrees; prompts therefore name `mcp__timeline-desk__*` and keep the prompt as the first CLI argument (`--mcp-config` is variadic). A terminal run without an exit file ends once no process carries its session id (`work_session.session_alive`, 60 s after its last launch); Stop workflow also records the open run as rejected (its terminal stays open until you close it). Reset (`reset_workflow`, `POST …/reset {confirm}`, confirm = the issue number) erases the task's workflow: its rows in workflows, workflow_runs, workflow_events, and qa_findings, and the `timeline/<id>/` folder (only inside a `timeline/` folder, never through the worktree link); it refuses while a terminal run is open; the worktree, branch and `task_events` stay.

`work_session.py` holds the git and terminal side: the Work tab (`GET /api/work/worktrees`, `POST /api/work/remove`), `worktree_for` / `prepare_worktree`, `terminal_command` (a terminal running `claude <args…>` that writes Claude's exit code to an exit file) and `launch_env`. Board → repo mapping (and `"me"`, your Timeline name) comes from the gitignored `timeline-desk.json` (example: `timeline-desk.example.json`; `TIMELINE_DESK_CONFIG` overrides the path), re-read per request. `prepare_worktree` reuses a worktree (by `<id>-…` branch or its folder) or `<id>-…` branch before creating `<id>-<slug>` from `origin/<base>` (`slugify` keeps the whole title; only `MAX_BRANCH`, the ref file-name limit, cuts it, at a word break); a new worktree's folder is `worktree_dir`: `<worktrees>/<repo name>-<id>`, never the branch name, and `link_timeline` makes the worktree's `timeline/` a symlink to the main checkout's (merging an older real folder in, adding `/timeline` to the shared `info/exclude` when git wouldn't ignore the link; best effort, a `note` in the result says what it left alone). Keep these rules: no permission-bypass flags; sessions are told never to push, open PRs or merge; removal uses `git worktree remove` and `git branch -d` without force and only for paths inside a configured worktrees folder; every POST is header-guarded. The page's badges (`workflowLink` in `app.js`) only link to the task page; nothing on the board launches Claude. Tests in `tests/test_work_session.py` run real git against temporary repos (no network).

`release_check.py` builds the release report for duell-admin (`build_report`), following `skills/release-pr-check/SKILL.md` minus the judgement parts. It is git/GitHub-specific, so it lives apart from `panteon_client.py` and gets Timeline statuses through an injected `status_lookup`; a Timeline failure sets `timeline_error` instead of failing the report. The checkout comes from `DUELL_ADMIN_DIR` / `--repo-dir` / `../duell-admin` and must have `origin` = Panteon-norway/duell-admin. Keep it read-only: fixed argument lists through the injectable `runner` (no shell), only `git remote/fetch/log/rev-list` and `gh pr list` / `gh release list`; `POST /api/release` is header-guarded because it runs `git fetch`. Tickets on QA are qa-release merges in `origin/master..origin/qa-release` whose merged commit (second parent) isn't in `origin/master`; a master PR went "via QA" when its tip has no non-merge commits outside qa-release and master. Tests in `tests/test_release_check.py` use a fake runner. The Release view deliberately shows only the pending PRs (`prs`, each with its `body`) grouped by base branch; the report's tickets, mismatches and notes are not rendered. `scripts/dashboard-service.sh` installs it as the `timeline-desk` systemd user service (WorkingDirectory = repo, so snapshots land in the repo's `timeline/planner/`, the same place the scheduled briefs write); after changing dashboard code, run `scripts/dashboard-service.sh restart`. `.claude/launch.json` attaches the preview to that running service instead of starting a second copy.

### Request log

Every call to Timeline (`_api_get`, the project-tasks POST, the dashboard image proxy) goes through `timed_request`, which appends one JSON line (`time`, `source`, `pid`, `method`, `path`, `status`, `ms`, `error` on connection failures) to `logs/timeline-requests-YYYY-MM-DD.jsonl` (`PANTEON_REQUEST_LOG_DIR` overrides; gitignored). Path only: no query, headers or credentials. Logging never raises. Route any new Timeline call through `timed_request` so the daily count stays complete.

### Markdown rendering contract

`render_task_markdown` produces a `task.md` (header: ID, Title, Creator, Date Created, Status, Tags; comments by the task creator are labelled "(task creator)" in their heading) with a fixed section order (Description, User-Provided Context, Conversation, Acceptance Criteria, Open Questions, Images). Two markdown "layers" are intentionally kept apart: the document's own structure is plain markdown, while all original content (task description, each comment) is wrapped in a fenced code block via `_as_code_block`, sized to a backtick run longer than any backticks already in the content, so embedded content can never break out and corrupt the document structure. Image URLs found inside that content are rewritten to absolute URLs (`absolutize_markdown_images` / `_resolve_url`) before being embedded, since the file is meant to stand alone outside the browser.

`## Acceptance Criteria` and `## Open Questions` are always emitted as placeholders — they require reasoning over the description that this deterministic fetcher does not attempt, and are left for an AI assistant reading the file to fill in.

### Output location and side effects

Fetching always writes `<base>/timeline/<issue_id>/task.md`, where `<base>` is `PANTEON_TIMELINE_DIR` if set, else the current working directory (see `task_markdown_path`). The MCP server also exposes whatever was last written for an issue as a resource at `timeline://<issue_id>/task.md` (`server.py`'s `task_markdown_resource`), so a client can re-read a previous fetch without touching the filesystem directly.

When a fetched task has neither description nor comments, the MCP tool asks the user for optional context via `ctx.elicit` (only if the connected client supports elicitation); accepted input is folded into `task_meta["user_context"]` and rendered under its own section. The CLI does not perform elicitation — that behavior lives only in `server.py`.

### Authentication

`build_api_headers` in `panteon_client.py` accepts a bearer token or cookie either as function arguments (per-call override, used by the MCP tool's optional args) or via `PANTEON_BEARER_TOKEN` / `PANTEON_COOKIE` env vars, loaded from a `.env` sitting next to `panteon_client.py` (not the caller's cwd) so credentials resolve regardless of which project the server is launched from. 401/403 responses are translated into a `PermissionError` with a consistent message; missing credentials raise before any request is made.

## Plugin packaging

The repo doubles as a Claude Code plugin (`panteon-timeline`): `.claude-plugin/plugin.json` (manifest), `.claude-plugin/marketplace.json` (so the repo can be added as a marketplace), the `mcpServers` entry inside `plugin.json` (launches `server.py` via `uv run`, credentials from the caller's environment since the installed copy has no `.env`; deliberately not a root `.mcp.json`, which Claude Code would also load as a project-scope config where `${CLAUDE_PLUGIN_ROOT}` is undefined), `skills/task-spec/SKILL.md` (fetch a task → write `timeline/<issue_id>/spec.md`, then stop for review), and `skills/my-day/SKILL.md` (read-only morning brief built on the single `get_my_day` call: planner `now` + soon-due `next` tasks, changes since the last snapshot, latest conversation on the top 3, a recommended starting task), and `skills/release-pr-check/SKILL.md` (duell-admin-specific, moved here from duell-admin's `.claude/skills/`: open PRs into `qa-release`/`master` vs the release-note format, QA approval via one `get_task_statuses` call, release-note drafts; must run from a duell-admin checkout because it uses `git`/`gh` there). Validate changes with `claude plugin validate .`.

The same repo also carries wrappers for other tools, all sharing the `skills/` directory: `gemini-extension.json` (Gemini CLI; validate with `gemini extensions validate .`), `.codex-plugin/plugin.json` + `.agents/plugins/marketplace.json` (Codex; skill-only, because Codex runs a plugin's MCP server with the plugin dir as cwd and `timeline/` would land in the plugin cache), and `.cursor-plugin/` (Cursor; untested). The `version` field is duplicated across `.claude-plugin/plugin.json`, `gemini-extension.json`, `.codex-plugin/plugin.json` and `.cursor-plugin/plugin.json` — bump them together. Do not add a root `.mcp.json`. The skill must not depend on edits to `task.md` — it is overwritten on every fetch.

## Testing conventions

Tests live in `tests/`, named `test_*.py`; `conftest.py` exists solely to put the project root on `sys.path` so tests can `import panteon_client` without packaging. Prioritize unit tests for the pure helpers (`extract_issue_id`, `_normalize_date`, `extract_images`, `absolutize_markdown_images`, `render_task_markdown`) and mock `requests.get`/the shared session for API-call and auth-error behavior — no live Panteon credentials should ever be required for the automated suite.

## Security

Never commit `.env`, bearer tokens, cookies, or anything under `timeline/` (generated task exports may contain customer data). `.gitignore` already covers `.env`, `timeline/`, `.venv/`, and caches — keep it that way when adding new generated-output paths.
